# C5 independent review

Date: 2026-09-08. Scope: source review of Daemon retention and its lifecycle/Store integration, followed by Rust SDK run-route ownership. No production code or tests were changed by this review. This document does not constitute an independent review of whale-store, which this reviewer implemented.

## Findings and verification of fixes

Three concrete defects were reported during the first pass. The reviewed fixes address each original failure scenario; no remaining blocking finding was identified in that bounded follow-up. A later root-led cross-language comparison found one additional ordering defect, recorded below with a separate evidence boundary.

1. **Late terminal delivery registration could retire another connection's active run.** Previously `terminal_delivery` was published before retention registration, and registration checked only the reused `(thread_id, turn_id)` key. Now `crates/whale-daemon/src/retention.rs:34` verifies `Arc::ptr_eq` against the current registry entry, and `server.rs:1822` registers successful delivery before notifying close waiters. Failed delivery never registers eligibility. Session close gathers run Arcs and releases the registry lock before awaiting delivery, so this reordered notification introduces no registry/close wait cycle. `retention.rs:349` exercises delayed registration against a replacement identity and verifies the new active entry survives a sweep.

2. **An unconfigured Daemon clone could disable another clone's Store maintenance.** Previously every incoming message replaced the one weak Store reference with the receiving clone's optional Store. `retention.rs:106` now registers distinct Store identities in a deduplicated weak list; `None` does not remove existing bindings. The worker clones only weak candidates under the short synchronous lock, then upgrades and awaits one Store at a time after releasing all registry/configuration locks. Its captures do not form a strong cycle with the Daemon/Retention owner. `tests/retention.rs:914` uses two distinct live Stores and a request through the unconfigured clone, then verifies both are swept without requests to their configured clones. Sequential maintenance still depends on each backend operation returning; this is not a guarantee of bounded cleanup latency under a stalled custom backend.

3. **Cancelled queries leaked strong routes; one failed query could orphan another successful query.** `crates/whale-sdk-rust/src/lib.rs:687` now acquires a `QueryRouteLease` while holding the registry entry. `run.rs:168` separates query-only state from ordinary started runs. Acquire, observe and Drop consistently take registry entry before query ownership. The last unobserved query releases its exact Arc; another pending waiter protects the route, and a successful running snapshot retains it until `finished`. Snapshot-only terminal queries close their event sender, while previously observed live subscriptions remain open for final events. The lease owns an Arc while removing the registry entry, preventing RunState destruction inside the query lock; RunState's final Drop only cleans its exact weak-cache entry. Reader handling clones the route before event processing and removes it by Arc identity after completion. No reverse query-lock-to-registry acquisition was found. `retention_tests.rs:283` checks actual pending-request cancellation and route/cache cleanup; `:301` checks both error and abort interleavings with a second successful running query and a subsequently delivered finished event.

4. **A terminal query could close a route before another pending query established that the run was live.** The first Rust/Python fixes closed a snapshot-only terminal result immediately when no live evidence had yet arrived. If query A returned terminal while query B was still pending and B then returned running, A had already closed the stream and removed its route. Rust, Python and Java now retain the terminal candidate until the final query lease exits; any pending query or real notification that observes live work keeps the route until the actual `finished` event. The root agent added both response orders, real-stream-before-reply and failed weak-cache retry tests. This finding and its fixes were not part of the independent reviewer's follow-up; root verification is reported in the C5 ledger.

## Other checked boundaries

- Run expiration preserves owner-scoped accepted-ID tombstones; session close removes only that owner's records. Successful terminal delivery, rather than terminal snapshot visibility, gates TTL/count eligibility.
- Start holds the session execution reservation while determining its accepted ordinal. Finalization restores that ordinal even if cancellation/deadline wins before Core entry; rejected admission does not reserve a new ID. Durable attach restores the count from archived runs, so live expiration does not refund quota.
- Reviewed the existing backpressure/failure, active-run, cancelled-before-Core, quota, attachment, owner isolation and weak-worker tests. Their assertions cover observable responses, invocation counters or retained payload identity rather than only internal handler counts.

## Evidence limits

This pass read source and test bodies at the time of review; it did not rerun suites or add a deterministic full-transport schedule test. The Daemon identity regression directly controls registry replacement using real RunRecord objects, rather than forcing the complete EOF/reconnect interleaving. The reviewer saw attributed Daemon and Rust results but did not independently execute them. Subsequent root verification ran the final Rust, Python, Java, workspace and real-process combinations; it is not relabeled as independent evidence. No claim is made that all possible scheduler interleavings, backend failures or the Store subsystem itself have been independently verified.
